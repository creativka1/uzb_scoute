# UzStat Talent Tracker

Скаутинг и сравнение игроков лиг Узбекистана и Казахстана на Next.js 15, React 19 и TypeScript. Текущий рабочий источник матчевых данных — сохранённые ответы SofaScore. FootyStats и Opta пока не подключены к production-пайплайну и не смешиваются с расчётами. Интерфейс поддерживает русский и узбекский языки.

## Запуск и проверка

Нужны Node.js 22 и Python 3.11+.

```bash
npm ci
npm run dev
# http://localhost:3000
npm test
npm run typecheck
npm run build
```

Тесты работают без сети и ключей. HTTP-ответы в тестах синхронизации — изолированные синтетические fixtures; в рабочие данные они не записываются.

## Контракт данных

- Отсутствующее значение — `null`, в интерфейсе — `—`. Реальный ноль сохраняется. Возраст, рост, стоимость, гражданство, клуб и позиция не заполняются придуманными значениями.
- Статистика относится только к матчам с явным `eventId`, соревнованием, сезоном и подтверждённым составом. Игрок и исторический клуб связываются через сторону матча; `player.teamId` может отражать более поздний переход.
- Если метрика отсутствует хотя бы в одном сыгранном матче выборки, полный итог этой метрики — `null`. Известная часть остаётся в `observedTotals`, число наблюдений — в `metricCoverage`. Сырые ответы сохранены.
- `current`, `previous`, `two` означают конкретные сезоны из метаданных источника. `latest` выбирает один доступный сезон для всей лиги; индивидуальной подстановки прошлого сезона нет.
- Покрытие сезона отмечается как неполное, пока не пройдены все страницы и не получены составы всех завершённых матчей. Даже полное покрытие матчей не гарантирует наличия каждой метрики.
- Точная позиция берётся только из однозначного `player.positionsDetailed`, согласующегося с широкой позицией источника. Расчёты по порядку состава, схеме и heatmap сохраняются как неподтверждённые кандидаты, а не футбольные факты.
- Процентили сравниваются внутри одной лиги, сезона и широкой позиции. Для каждой метрики нужен минимум из трёх игроков с 450+ минутами. В интерфейсе исходный процентиль отделён от рассчитанного рейтинга с поправкой на минуты.
- Бюджетные замены требуют известных стоимостей и строго меньшей стоимости кандидата. Сохранённые кандидаты хранятся в этом браузере независимо от фильтров; очищение фильтров их не удаляет. Повреждённое локальное сохранение не перезаписывается автоматически.

## Политика источников данных

- **SofaScore — текущий первичный источник матчевого уровня:** матчи, составы, минуты и доступные player-event показатели. Именно эти данные сейчас участвуют в расчётах платформы.
- **FootyStats — кандидат на вторичный источник и сверку сезонных итогов.** До отдельного импорта и аудита покрытия его значения не подмешиваются к SofaScore.
- **Opta / Opta Analyst — не production-источник проекта на текущем этапе.** Подключение допустимо только при подтверждённом доступе/API и покрытии нужных лиг.
- Значения разных провайдеров нельзя усреднять или склеивать автоматически. Перед объединением сверяются competition/season/player IDs, матчи, минуты и базовые totals; существенное расхождение блокирует merge и помечается для аудита.
- В интерфейсе источник и полнота данных должны показываться отдельно от спортивной оценки игрока.

## Поток данных

1. `data/cache/seasons`, `lineups`, `players`, `heatmaps` — ответы источника.
2. `scripts/data_integrity.py` — проверка связей и детерминированная сборка `data/superliga_stats.json` и `data/audits/data_integrity.json`.
3. `scripts/build_detailed_positions.py` — подтверждённые профильные позиции и отдельно кандидаты.
4. `app/api/players/route.ts` — выбор периода, расчёт метрик и ролевых процентилей.
5. `app/page.tsx`, `lib/recruitment.ts`, `types/players.ts` — интерфейс, подбор и общий nullable-контракт.

`GET /api/players?league=UZB&season=latest` возвращает массив игроков и заголовок `X-Data-Metadata` с выбранным периодом и покрытием. Допустимы `league=UZB|KAZ|all`, `season=latest|current|previous|two`. Некорректный фильтр даёт 400; отсутствующий набор данных — 503; повреждённый — 500. Ошибки не маскируются успешным пустым массивом.

Пересборка без обращения к провайдеру:

```bash
python scripts/data_integrity.py
python scripts/build_detailed_positions.py
```

## Обновление источников

Для сетевых скриптов нужен `pip install curl_cffi`.

- **Sync verified match statistics** — ручной workflow для обеих лиг и двух сезонов. Требует существующий secret `RAPIDAPI_KEY`. Проходит страницы до `hasNextPage=false`, проверяет сезон ответа, считает реальные HTTP-попытки, сохраняет промежуточный кэш. Параметр `max_requests` ограничивает расход квоты, включая retries; значение по умолчанию — 1500. Это лимит, а не гарантированное число запросов для полного обновления.
- **Refresh player profiles** — ежедневное обновление профилей через публичный endpoint. Кэш с известной датой используется 24 часа. Ошибки доступа прерывают серию после десяти неудач и отмечают workflow как failed; старый ответ при сетевой ошибке сохраняется.
- **Sync SofaScore Heatmaps** — существующая ежедневная небольшая серия: максимум 12 HTTP-попыток. Пустые ответы временно кэшируются на 7 дней, ошибки — на час. 429 не считается успешной загрузкой.
- Каждый workflow сам пересобирает нужные производные файлы: push через `GITHUB_TOKEN` не используется как механизм запуска следующего workflow.
- Записывающие workflow выполняются последовательно. Ошибка сохраняет доступные промежуточные данные и отчёт, но не превращает неполный запуск в успешный.

## Ограничения восстановленного кэша

На момент исправления проверены 440 файлов составов: 185 связаны с описаниями матчей (99 UZB, 86 KAZ), 254 пока не имеют метаданных матча, один содержит ответ 404. Все исходные файлы сохранены. В проверенной выборке есть статистика 2025 года для 722 записей игроков; подтверждённой выборки 2026 года пока нет. Реестр содержит 895 записей «лига + игрок», включая игроков без проверенной статистики.

Поэтому выбор 2026 сейчас честно возвращает пустой список, а `latest` показывает явно подписанный 2025 год с предупреждением о неполном покрытии. Для восстановления остальных матчей нужно запустить исправленную синхронизацию и получить недостающие ответы источника. Полнота и точные позиции не появятся только от пересчёта старых файлов.

## Интерфейс и развитие платформы

Основные разделы: «Игроки», «Поиск под задачу» и «Сохранённые». В профиле обзор отделён от полной статистики; игрок, второй выбранный игрок и среднее по позиции показаны на одной шкале в исходных единицах. Покрытие, размер выборки и методика доступны в раскрываемом пояснении. Необозначенные P/N больше не используются.

Следующий продуктовый этап и критерии готовности: [анализ команды и матчей](docs/platform-roadmap.md).

## Команды, матчи и прозрачные показатели

Вкладка «Команда и матчи» разделена на «Обзор», «Матчи», «Состав» и «Выводы». Обзор сравнивает последние и предыдущие 5 или 10 доступных матчей. Матч открывается отдельным представлением со счётом, выбором стороны и одной дополнительной метрикой. Из состава доступны профиль игрока и поиск усиления по позиции с сохранением периода и контекста команды. В «Матчах и динамике» игрока дата открывает соответствующий матч команды. Доступны поиск соперника и игрока, разбор соперника, сравнение сезонов и широких позиций источника.

Выводы, решения/цели и критерии проверки сохраняются в localStorage этого браузера вместе с периодом, ID матчей и снимком основания. Сохранённый вывод можно редактировать; исходные матчи и снимок основания сохраняются. Результат проверки отмечается вручную. Доступны JSON-экспорт и восстановление. Это пока не облачное многопользовательское рабочее пространство.

График «Сравнение со средним» показывает исходные значения: при нуле полоска пустая, при пропуске — прочерк. Вертикальная отметка на полосе игрока — среднее арифметическое той же позиции, лиги и периода. В базу входят игроки с ≥450 покрытыми минутами и ≥80% покрытия метрики; при группе меньше трёх среднее не рассчитывается. Шкала каждой метрики общая для обоих игроков и среднего, от нуля до максимума группы/выбранных игроков (для процентов — 100). Граница шкалы подписана: полная полоса не означает 100% успешности. Дублирующее переключение «Значения / Место в группе» убрано.

Скаутский индекс возвращён в таблицу и профиль: среднее доступных ролевых процентилей с поправкой на покрытые минуты. Состав индекса раскрывается в пояснении. Наборы могут отличаться, поэтому индекс — предварительный ориентир, не универсальная оценка качества. Схожесть по умолчанию не зависит от цены; «только дешевле» требует известной меньшей стоимости. Используются одна лига, одинаковый явный период, широкая позиция и фиксированный набор осей исходного игрока: минимум 3, для GK — 2. Все кандидаты должны иметь этот набор. Схожесть = 100 минус среднее абсолютное расстояние процентилей; это не вероятность удачного трансфера.

Пересборка всех производных данных:

```bash
python scripts/data_integrity.py
npm test
npm run build
```

- `data/superliga_stats.json` сохраняет строгий агрегат: полная сумма только при покрытии всех загруженных участий.
- `data/metric_observations.json.gz` содержит наблюдаемые суммы, покрытые минуты, ID матчей и парные знаменатели процентов. API показывает частичные значения вместе с покрытием.
- `data/match_core.json.gz` содержит нормализованные команды, игроков, матчи и участия, явные ID соревнования/сезона, путь к сырому составу и SHA-256. Это файловое ядро первого выпуска; PostgreSQL ещё не внедрён.
- `data/audits/metric_coverage.json` считает наличие полей по участиям в каждой лиге, не по уникальным игрокам. Сейвы нельзя оценивать по общей доле всех полевых игроков.

Gzip-файлы — обычный JSON в стандартном сжатии. Пересборка детерминирована, исходные кэши не меняются. Workflow синхронизации пересобирает все производные файлы после обновления источников.

`/api/players` отдаёт `statsMetricDetails`, `roleMetricCoverage`, `roleBenchmarks` (среднее, максимум и размер группы по метрике), `statsSeasonIds`. Per90 использует только минуты матчей с известным показателем. Проценты используют числитель и знаменатель из одной выборки; отсутствие попыток не равно 0% успешности. Наблюдаемый ноль остаётся нулём, отсутствие данных — null.

База процентилей по метрике: ≥450 покрытых минут и ≥80% минут загруженной выборки. Для оценки игрока: ≥90 покрытых минут и ≥60% покрытия. Группа меньше трёх игроков не даёт процентиль. Это правила платформы, не гарантия достоверности: пропуски могут быть неслучайными, и без подтверждённого контракта источника их нельзя считать нулями.

`GET /api/analysis?league=UZB&seasonId=72383` возвращает матчевое ядро сезона. Дополнительные `teamId` и `playerId` фильтруют набор; для команды остаются обе стороны её матчей. Неизвестный сезон/плохой фильтр — 400, отсутствующий файл — 503, повреждённый файл — 500. Явный сезон не подменяется прошлым. Без `seasonId` возвращаются сохранённые периоды для выбора в UI.

Ограничения: подтверждены 185 составов сезона 2025; 254 состава не связаны с метаданными матчей. Для 2026 подтверждённой выборки нет. Нужен запуск Sync verified match statistics с действующим RapidAPI-ключом и квотой; новые запросы провайдеру в этом выпуске не выполнялись. «Последние» означает последние доступные матчи. Событийных данных для карт ударов, сетей передач и PPDA нет; такие данные не имитируются. Браузерная E2E/визуальная проверка не завершена из-за блокировки локального адреса в браузере среды.


## Завершённый цикл анализа решений

1. Откройте «Команда и матчи → Состав». Видны игры, ниже минуты, доля суммарного времени команды и раскрываемая глубина по позициям источника. Точные позиции без подтверждения остаются неизвестными.
2. Нажмите «Сформулировать потребность» в группе глубины или выберите позицию и «Найти усиление». Запишите наблюдение и требования. Поиск получает явный сезон и позицию; кнопка на карточке добавляет кандидата именно к этой потребности.
3. Вернитесь к команде во вкладку «Выводы». У кандидата выберите «Принять решение» или создайте самостоятельное решение для команды/игрока. Укажите действие, метрику, порог и горизонт 3/5/10 игр.
4. Сохраняется исходный снимок. После обновления матчевого ядра откройте вкладку снова или нажмите «Перечитать данные»: появятся сравнение до/после, изменение, покрытие и выполнение числового критерия. Сохраните проверку с комментарием. Доступен экспорт/восстановление всех потребностей и решений.

Обычный режим использует только игры после времени сохранения решения. Для проверки на уже имеющейся истории выберите явно помеченный ретроспективный режим и матч отсечки. Анализ остаётся внутри выбранной лиги и сезона. Игрок оценивается по следующим доступным участиям, в том числе в других клубах; это не свидетельство трансфера. Порог покрытия — 80% игр/участий с метрикой; при нехватке данных результат — «Недостаточно новых данных». Старые матчи, загруженные позднее, не считаются новыми результатами.

`lib/decisions.ts` рассчитывает и валидирует снимки, критерии, связанные потребности и решения; `hooks/use-decision-store.ts` защищает локальное хранение. Исходная оценка фиксируется, даже если источник позже изменился. Заметки старого формата сохраняются отдельно. В карточке матча раскрывается покрытие всех показателей выбранной стороны, по игрокам и минутам; сейвы — только по вратарям.

Границы этого выпуска: единый пользователь в браузере, данные подтверждённого доступного сезона, уведомление о готовой проверке внутри вкладки. PostgreSQL, облачная совместная работа и новые данные провайдера не заявляются выполненными. Визуальная браузерная проверка остаётся заблокированной средой; проверены расчёты, реальные обработчики цепочки потребность → кандидат → решение → проверка, сохранение и восстановление, ошибки и production-сборка.
